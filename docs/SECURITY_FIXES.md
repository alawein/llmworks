# Security Status Notes

Last updated: 2026-07-11

This document records the current security posture of the repository. Earlier
drafts claimed a client-side API-key encryption path and AES-256 encryption at
rest. That implementation is not present in the current codebase, and those
claims must not be repeated until code, migrations, and tests support them.

## Current implemented controls

- Supabase authentication configuration lives in `supabase/config.toml`.
- Application data access is backed by Supabase migrations and generated
  TypeScript types.
- Benchmark run tracking uses row-level security on `benchmark_runs` and
  `benchmark_results`.
- Security-related initialization modules are wired from `src/App.tsx`.
- Provider keys and encryption salts are treated as deployment secrets only.

## Current non-claims

Do not claim any of the following for the current app:

- server-side provider-key encryption at rest;
- client-side provider-key encryption;
- AES-256 encryption for provider keys;
- immutable audit trails for every action;
- cryptographic proof or verifier guarantees;
- compliance-ready reports.

## Provider-key handling rule

Provider integrations must keep keys server-side when real provider calls are
implemented. Do not reintroduce `VITE_API_KEY_ENCRYPTION_SALT` as a public client
configuration value unless the design is reviewed and tested.

## Benchmark security notes

The benchmark queue tables are user-owned. The current edge function queues run
records only; no provider prompts, outputs, or scored results are generated by
the current implementation.

## Verification checklist

Before claiming a new security control:

1. Add or update the implementation.
2. Add migrations or configuration as needed.
3. Regenerate Supabase types when schema changes.
4. Add tests that fail without the control.
5. Update this document and product copy in the same PR.
